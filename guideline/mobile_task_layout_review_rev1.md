# モバイル：ヘッダーと主要タスク領域のレビュー補足（案）

## 1. 位置付け

[共通ガイドラインrev2](uiux_review_guideline_rev2.md)のP01・P06・P08、NAV-01/03、CON-01/02、A11Y-03/05、RSP-01を具体的に適用するための判断補足。新しい共通L2 Mustを追加するものではない。

今回確認したサービスはschmatzのみ。具体的な追加要件は[L3プロファイルrev3案](../profiles/uiux_profile_schmatz_rev3.md)のSCH-09〜11へ置く。共通化には、既存の「2サービス以上」の実績条件と版更新・レビューを適用する。共通ガイドラインrev2本体は変更していない。

## 2. ヘッダーを機能と見た目に分ける

「上にヘッダーがあるべきか」ではなく、その行が何の役割を担うかを確認する。アプリ共通ヘッダー、ページの見出し、カードの見出し、テーブルのヘッダーは別物。本補足は前3者が対象で、表の列見出しを削除する指示ではない。

| 役割 | 残す条件 | 統合・省略を検討できる条件 |
|---|---|---|
| サービス識別 | どのサービスを使っているか判断できる | ロゴ専用の独立行は不要。短いサービス名を他の上部情報と統合できる |
| 現在地・戻る手段 | ページ見出し、ナビ選択状態、必要な戻る操作が機能する | 同じ「ホーム」を示すパンくずとロゴリンク等を重複させる理由がない |
| 利用者・会社・アカウント操作 | 代理操作、複数会社、実ログイン等で誰の情報か確認できる。既存のログアウト等へ到達できる | 装飾アバターだけで独立行を占める。削除しても必要情報は別の一貫した場所に残る |
| ヘルプ | 同じ画面群・ブレークポイントで見つけやすい場所にある | 下部ナビ等と完全に同じ遷移先なら重複アイコンを省ける。唯一の導線は消さない |
| ページ見出し | h1等の意味・読み上げ・遷移後フォーカス、対象範囲が維持される | 見出し専用の広い帯を別に設けず、主要コンテンツ先頭や共通の上部領域へ統合できる |

独立行を統合することと、サービス名・現在地・利用者確認・ヘルプを削除することを混同しない。上部を隠すだけのCSSではなく、役割の移動先まで設計する。ホームだけ別の場所へ主要ナビを動かし、画面ごとに覚え直させる変更を避ける。

### 参照元の適用範囲

SmartHRの「ページレイアウト」は同社のページにAppHeaderを配置する構成を示し、AppHeaderのモバイル版もヘッダーを保持している。したがって「SmartHRがヘッダーの削除を推奨している」とは説明しない。SmartHRのアカウント・企業・複数アプリを扱う前提と、自サービスの役割・導線を比較し、異なる構成を選ぶ理由をL3へ記録する。[S1][S2]

WCAG 3.2.6は、複数ページに繰り返すヘルプの相対的順序を扱う。独立した上部ヘッダーを指定するものではない。同じ画面幅でヘルプを下部へ統一する案は評価可能だが、ページごとに入れ替えるだけでは一貫性を満たさない。[S5]

## 3. 「今日の研修」を一つの面積で評価しない

表示領域を、(a)導入・見出し、(b)対象の識別情報、(c)現在の状態、(d)操作に分ける。

- 導入・見出し：挨拶、ロゴ専用行、同じ説明・日付の繰り返し、大きな帯を先に整理する。
- 識別情報：対象日、コース名、講座名、時間、判断に必要な会場を残す。短い名称は自然に収まる配置にし、長い名称や複数研修は必要な高さを使う。
- 状態：未連絡、受付済み、実績未確定／確定済み、エラーは主要コンテンツ。受付時刻や未保存の警告を「補足」として消さない。
- 操作：主要タスクのボタンと安全な例外連絡の入口は主要コンテンツ。ボタンが大きいことだけでカードを過大と判定しない。

「今日の研修」という見出しは対象日とともに業務ブロック先頭へまとめる案を比較する。見出し構造は保ち、対象0件でも現在地を失わせず、複数研修ではページ見出しを複製しない。研修カード全体を折りたたみ、出席連絡の前に余計な操作を増やす対応はしない。

## 4. 縮小する順序と数値の扱い

独立行の重複整理 → 情報のグルーピング → 余白・罫線の重複整理 → 役割に応じた文字の強調、の順で比較する。操作領域や必要情報を削ってスペースを確保しない。

文字サイズ・行送り・余白には、既存のプロジェクトトークンか、採用理由と置換予定を記録する。外部規格の要求、参照デザインシステムの値、自サービスの採用値、受入時の計測値を別欄にする。h1/h2というHTML要素だけで文字サイズは決まらない。

SmartHRのブロックタイトルはM・bold、タイポグラフィのMは16pxである。これは識別用タイトルの参考値で、全サービスの見出しやカード高を一律に決める規格ではない。[S3][S4]

「ヘッダーは必ず何px以下」「今日の研修は画面の何%以内」という未検証の共通閾値は作らない。画面占有率を記録する場合は分母（CSS viewport、ブラウザUI・固定ナビ等を含むか）と内訳を明示し、状態・操作まで不要領域に数えない。特定画面の1データで数値を満たしても、読みやすさの承認にはしない。

## 5. レビューで残す証拠

| 観点 | 記録すること |
|---|---|
| 機能の保存 | サービス識別、現在地、利用者・会社確認、ヘルプ、戻る・終了の移動先 |
| 垂直方向の配分 | 同一viewportで上部導入、業務開始、状態、主操作、固定ナビの位置を修正前後で記録 |
| 通常条件 | 対象日・研修・状態が分かり、主要操作が初期表示で押せるか |
| 例外条件 | 長文、複数件、0件、エラー、文字拡大、設定展開、キーボード・safe areaで欠落や遮蔽がないか |
| 一貫性・構造 | 同役割の隣接画面、h1と見出し順序、スクリーンリーダー、フォーカス、PC／他役割への影響 |
| 人による判定 | 対象・状態・次の操作を説明できるか。一次評価と最終承認、未確認を区別する |

WCAG 1.4.10は必要な縦スクロールを禁止しない。文字や機能を切って1画面に収めない。[S6] WCAG 2.4.11のAA要件はフォーカス対象の完全遮蔽を防ぐことであり、主要操作を全体表示する自社基準はこれと区別する。[S7]

本補足の追加だけでUIの指摘をfixedにしない。実装・比較・受入は別工程。以前のCI成功を新しい上部レイアウトの合格証拠に流用しない。
